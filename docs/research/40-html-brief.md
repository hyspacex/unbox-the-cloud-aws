# Brief: the Keel explainer and demo page

Deliverable: one self-contained HTML file, `demo/keel.html`, that explains Keel and lets a reader click through the review transaction with the live-slice fixture data. No build step, no external network calls, no frameworks that need a bundler. Inline CSS and vanilla JavaScript. Fixture JSON is embedded in the page as a script block so the file opens from disk. It must render well at 1440 wide on a projector and degrade acceptably at 1024.

Source of truth: `docs/research/30-design-v3.md`. Fixture data: the FULL fixture in `demo-data/lantern/` (profile-us-bank.json with eight controls, snapshots.json, expected-findings.json, ledger.json, agent-trace.json, the five documents including architecture v2 and v3 and the runbook). `demo-data/lantern/live-slice/` is the three-control fallback and is not used by the page. `profile-eu.json` is the alternate profile for the explainer toggle.

## Audience and tone
Tech execs and engineers at a Box plus AWS hackathon, and the team's own teammates tomorrow morning. The page is read in two ways: scrolled top to bottom as an explainer in five minutes, and driven live as the three-minute demo. Plain English, short sentences, no marketing adjectives. Every number on the page comes from the fixture or is labelled illustrative. The mode label (Mock, fixture data) is visible at all times.

## Page structure, in order

1. **Title block.** "Keel." One line: "Know what changed, and who reviewed that exact evidence." Tagline under it: "Files have versions. Compliance evidence should too." One sentence of what it is. Mode label.
2. **The problem in one picture.** Two document excerpts side by side, v2 and v3 of the architecture doc, section 4.3, with the key-management sentence highlighted in v2 and struck in v3, the replacement text marked. Under it one line: "A hash says the page changed. A reviewer needs to know which control lost which clause, whether it survives elsewhere, and who reviewed which version."
3. **How it works.** The ten-step review transaction from spec section 3 rendered as a horizontal strip of steps with one line each, with Box steps, Bedrock steps, and code steps colour-coded. A legend: Box, Bedrock, application code, human.
4. **The interactive demo.** This is the core. A single "package view" panel with the eight control rows on snapshot S2 (reviewed baseline), named fixture reviews, then a "Submit rewritten architecture document" button. Pressing it plays the agent-trace with real-looking timing (compressed to about 8 seconds, with a "compressed" note), streaming application and agent events into a trace panel, then updates the rows to their S4 outcomes with the displayed statuses computed by the sixteen ordered rules from spec section 4, including the verification-holds and materiality logic from section 3 step 7 (implement the rules in JavaScript, do not hardcode the labels). After the submit, six rows must read "Verified, holds", SEC-ARCH-22 "Needs review: evidence binding changed", SEC-ARCH-07 "Needs review: key-management evidence missing", and the count line must read from the computed statuses. Clicking the SEC-ARCH-07 row opens the finding card exactly as described in spec section 6: control block with required clauses and per-clause marks, machine assessment block labelled as machine, two-column quotes with word-level diff, related controls, human disposition with built actions (Return to author, Verify disabled with reason) and proposed actions visually separate. Pressing Return to author shows a modal standing in for the Box task: reason prefilled from the fixture, author, due date; on confirm the ledger gains the response and author-task events, the row flips to "Returned to author, open," the secondary line shows the reviewer identity "as returned by Box (fixture)", and a small author-task panel appears for three seconds. Clicking SEC-ARCH-22 shows the counterexample card with the runbook quote and a one-click "Acknowledge binding, re-verify" that flips it to "Verified" with Dana's fixture message. Clicking any holding row shows the verification_holds event and the materiality rule that let it hold. A "Reset" link returns to S2.
5. **Ledger and export.** Table of events from ledger.json, filterable by control, with expandable records showing snapshot id, model id, prompt hash, chain hash. An "Export" button that downloads the CSV plus manifest from the in-page data and a visible limitation line: "Observed revisions, evaluations, and responses from this run. Complete-period reconciliation and independent integrity protection are not implemented."
6. **Status rules, published.** The sixteen ordered rules from spec section 4 as a readable list, the stored-field definitions, and the staleness and materiality rule from section 3 step 7. Short.
7. **What Box does, what AWS does, what code does, what a person does.** Four columns, five bullets each max, from spec sections 8 and 9. Then the architecture strip: built components in solid boxes, proposed components in dashed boxes, labelled "built Saturday" and "proposed." Local ledger named.
8. **Positioning.** Four short paragraphs from spec section 9. No competitor named as unable; use "we did not find."
9. **Control profiles.** The US bank profile (the one the demo runs) and the EU alternate as a toggle, each control showing id, title, requirement, required clauses, tier, framework map labelled illustrative, and the materiality setting per tier. One line: "The engine is control-agnostic; the profile is the bank's."
10. **Readiness.** Three columns: built, proposed, pilot gates, from spec section 10. Then "Measured and claimed" from section 11 verbatim in spirit.
11. **The three-minute script.** The table from spec section 7, so a presenter can read it from the page.
12. **Footer.** Synthetic data notice; names are fictional; model id and inference profile; link text to the spec and research files by path.

## Visual direction
Restrained, document-like, high contrast. One accent colour for "needs review" (amber), one for human-recorded dispositions (deep blue), grey for machine assessments. Never green for a machine result; green only for a human Verified on the current snapshot. System font stack. Generous whitespace. Monospace for ids, hashes, quotes. Word-level diff with strike and underline, not red/green fills. No icons that need a font. No animation except the trace stream and the row status flips.

## Correctness requirements
- The displayed status for every row is computed by the eight rules in JavaScript from the stored fields in the fixture. A reviewer of the page can change a stored field in the console and watch the label follow.
- Every quote displayed must be present verbatim in the embedded document text; the page should verify this on load and show a small "quotes validated: n/n" indicator.
- Machine assessment text never contains "satisfied", "compliant", "passed", or "regressed".
- Counts on the package view are computed, not typed.
- No external resources. Opening the file from disk with no network must work.

## Acceptance
Open the file, scroll it as an explainer in five minutes, then run the demo path: baseline, submit, trace, hero card, counterexample card, return to author, ledger, export. Everything in the spec's demo table must be reachable in that order with no dead ends. Then check: the hero row says "Needs review: key-management evidence missing" before the action and "Returned to author, open" after; SEC-ARCH-22 says "Needs review: evidence binding changed" and then "Verified" after the acknowledgment; the six other rows say "Verified, holds"; the count line matches at every step.
